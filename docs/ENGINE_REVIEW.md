# 파티 게임용 2D 물리 — 엔진 검토

목표: 마리오 파티류 미니게임 모음 (횡스크롤 플랫포머, 탑다운, 물리 난장판, 조인트/탑 쌓기 등)에서 같이 쓸 물리 기반.
결론부터: **강체 물리는 Planck.js(Box2D 포팅)를 엔진에 넣고(`World2D`), 던전 게임이 쓰는 기존 `Physics`(킨메틱 쿼리)는 그대로 둔다.**

## 1. 기존 `Physics` / `Collider2D` / `Rigidbody2D` 평가

던전 게임(탑다운, 벽·장애물·탄·근접 휘두르기)에 맞게 만든 **킨메틱 충돌 질의 라이브러리**다.

| 되는 것 | 안 되는 것 (파티 게임에 필요한 것) |
|---|---|
| 원/상자/캡슐/둥근 상자, 격자 광역탐색, 스윕 이동(터널링 없음), 부채꼴·굵은 선 질의, 트리거/충돌 이벤트 | 중력, 질량/관성, 마찰·반발 해결(솔버), 쌓기·밀기, 회전하는 강체끼리의 충돌 |
| 할당 없는 질의, 던전 규모(수백 개)에서 가볍다 | 조인트(경첩/스프링/밧줄), 슬라이더, 모터 |
| | 한쪽 통과 발판, 이동 발판에 실려 가기 |

`Rigidbody2D`는 속도·감쇠·반발만 있는 "가벼운 강체"이고 솔버가 없다. 물리 장난감(Tricky Towers, Gang Beasts 류)이나 플랫포머의 이동 발판·조인트에는 부족하다. 이걸 키워서 솔버·조인트까지 직접 만드는 것(옵션 A)은 Box2D가 20년 걸려 다듬은 안정성(쌓기, 연속 충돌, 조인트)을 다시 만드는 일이라 비용 대비 효과가 낮다.

## 2. 후보 비교

| 기준 | A. 직접 확장 | **B. Planck.js (Box2D)** | C. Matter.js | D. Rapier2D (WASM) |
|---|---|---|---|---|
| 플랫포머 감각 | 컨트롤러만 만들면 최고 (완전 통제) | 컨트롤러 + 마찰 0 + 상대속도 제어로 충분 (이 구현으로 확인) | 가능하나 접촉 처리가 거칠다 | 최고급 |
| 쌓기·혼돈 | 직접 구현 필요 | 안정적 (10단 탑, 서로 다른 크기의 더미 확인) | 대칭 10단 탑은 통과(직접 확인). 다만 비대칭 쌓기·긴 조인트 사슬은 흔들리는 경향이 알려져 있음(이번엔 미검증) | 매우 안정적이라고 알려져 있음(미검증) |
| 조인트 | 직접 구현 | 회전·거리·용접·밧줄·슬라이더·바퀴·마우스·모터 전부 있음 | 제약(constraint)이 "부드러운 스프링" 기반이라 딱딱한 경첩/모터가 약함 | 있음 |
| 연속 충돌(터널링) | 스윕이 있음(원만) | `bullet` + 정적 지형에 대해 기본 연속 충돌 (6000 u/s 탄이 2유닛 벽을 못 뚫음, 확인) | **없음** | 있음 |
| 크기 | 0 | 297KB (gzip ≈ 55KB) | 83KB (gzip ≈ 26KB) | **1.5MB** (gzip ≈ 580KB, wasm 포함 `compat` 빌드) |
| 오프라인 동봉 | 해당 없음 | 한 파일(`planck.min.js`)을 저장소에 넣으면 끝 | 한 파일 | wasm을 base64로 포함한 빌드 + 비동기 `init()` 필요 |
| 결정성 | 가능 | 같은 입력·같은 스텝이면 같은 결과가 나오는 구조 (이번에 시드 재현 테스트까지는 안 함) | 대체로 | 문서상 결정적 모드 제공 |
| 속도 (200개 상자, node, 같은 조건) | — | 약 1.3~1.9 ms/스텝 | **약 0.2 ms/스텝** | WASM이라 가장 빠를 것 (측정 안 함) |
| Y-up 통합 | — | Box2D도 Y-up: 변환 없이 `Transform`과 1:1 (단위만 스케일) | Y-down이라 뒤집어야 함 | Y-up |
| 라이선스 | — | MIT | MIT | Apache-2.0 |

측정은 이 저장소의 같은 상황(200개 상자, 바닥+벽)에서 했고, Rapier는 크기만 직접 확인하고 속도는 재지 않았다(WASM 지원이 약한 TV 브라우저에서 실패할 위험이 있어 이번에는 후보에서 뺐다).

### 선택: B. Planck.js
- 조인트·모터·한쪽 통과·연속 충돌까지 필요한 게 **전부 검증된 알고리즘으로** 이미 들어 있고, Box2D 레퍼런스가 풍부해서 미니게임 담당 에이전트들이 문서를 찾기 쉽다.
- Y-up, 월드 단위(32 = 1m) 스케일만 맞추면 Transform과 바로 연결된다.
- Matter.js보다 느리지만(200개 상자 1.3 ms vs 0.2 ms, node 기준) **파티 게임 한 판의 몸체 수는 보통 20~80개**라 여유가 있고, 쌓기·조인트·연속 충돌의 정확성이 더 중요하다.
- Rapier는 가장 빠르고 정확하지만 번들이 5배 크고 비동기 초기화·WASM 의존이 생긴다. 나중에 TV에서 몸체 수가 문제가 되면 그때 같은 `World2D`/`Body2D` 인터페이스 뒤로 교체할 수 있다 (게임 코드는 `planck`를 직접 쓰지 않는다).

### 약점과 대응
- **Planck는 Vec2를 많이 할당한다** → 게임 쪽에서 쓰는 경로(`Body2D` 속성, 질의)는 할당을 줄여 두었고, 느린 기기에서는 월드가 자동으로 1/30초 스텝으로 내려가 끊기는 대신 느려지게 한다 (`adaptive`).
- **한 프레임 최대 3스텝**: 프레임이 밀려도 따라잡기 폭주(spiral of death)가 없다.
- **절대 몸체 수 한계**: 아래 성능 표 참고. 약한 TV를 가정하면 한 장면의 활성 몸체는 ~60개 안쪽을 권장.

## 3. 구현 (`KuntoGame/physics/World2D.js`, `Controllers.js`)

- `KuntoGame/vendor/planck.min.js`(MIT, 무수정)를 `kuntogame.js`에 포함 → CDN 의존 없음. 던전에는 번들 크기만 늘어난다(로드 시간 영향은 측정상 미미, 아래).
- `World2D`: 고정 스텝(1/60)+누산기+보간, 레이어(충돌 분류), 레이캐스트/AABB/점/원 질의, 조인트 7종, 접촉 이벤트, 디버그 표시.
- `Body2D` 컴포넌트: dynamic/static/kinematic, 상자·원·캡슐·다각형·선분·체인, 센서, 한쪽 통과 발판, 충돌 콜백.
- `PlatformerController`(가변 점프·코요테·선입력·이동 발판 타기·발판 아래로·벽 슬라이드/점프·추가 점프), `TopDownController`(가감속·대시).
- 엔진 변경은 `Engine._frame`에 `system.postUpdate` 훅 한 곳뿐 (update → 물리 스텝 → lateUpdate → 렌더 순서 보장). 이 훅이 없는 시스템에는 영향이 없다.

## 4. 측정 (이 저장소의 `docs/physics-demo.html` + 헤드리스 크로미움, 소프트웨어 렌더)

| 조건 | 몸체 | 평균 물리 ms/프레임 | 최대 | 엔진 프레임 ms | fps |
|---|---|---|---|---|---|
| CPU 1x, 계속 휘저음(전원 깨어 있음) | 64 | 0.63 | 2.4 | 0.98 | 60 |
| CPU 4x 느림 | 64 | 2.9 | 8.4 | 4.3 | 60 |
| CPU 1x | 204 | 2.2 | 4.4 | 2.9 | 60 |
| CPU 4x 느림 | 204 | 15 | 44 | 18.5 | 22 (자동으로 30Hz 스텝으로 전환됨) |

해석: **60개 안팎은 4배 느린 CPU에서도 60fps**. 200개가 전부 깨어 있는 최악의 장면은 4배 느린 CPU에서 22fps까지 내려가므로, 약한 TV용 미니게임은 활성 몸체를 60~80개로 제한하고, 쌓아 둔 몸체는 잠들게 두는 것이 좋다.

## 5. 테스트

`docs/`의 데모 페이지를 가짜 시간(정확히 1/60초씩)으로 돌려 결정적으로 검증했다. 항목: 낙하/정지/수면, 가변 점프, 코요테·선입력, 한쪽 통과 발판(위/아래/내려가기), 10단 탑, 조인트 사슬·모터·슬라이더·스프링·용접·밧줄·마우스·바퀴, 접촉 이벤트(begin/end/pre/post/센서), 콜백 안 destroy 안전성, 레이캐스트·질의, 이동 발판 타기, 보간(144Hz), 연속 충돌, 캡슐이 타일 이음매에서 안 걸림, 단위·질량, 월드 재생성, 탑다운 컨트롤러.
던전 게임은 변경 없이 로드·실행됨을 확인(보스 패턴·난이도·큰 방 회귀 테스트 통과).
